## 写作目标

一篇好的学术讲解不是知识清单，也不是代码仓库。它应帮助读者完成三次转变：

1. 从“不知道问题为何困难”到能指出朴素方法的瓶颈；
2. 从“记住结论”到理解状态、公式或不变量为什么成立；
3. 从“看懂模板”到能在新题中识别条件、选择方法并正确实现。

文章应同时保证：

- **准确**：定义、命题、边界和复杂度经得起核对；
- **可学**：信息顺序符合读者建立模型的过程；
- **可用**：例题与代码把抽象结论落实到解题过程；
- **有层次**：主线完整，拓展明确，但不让次要内容淹没核心。

## 读者的认知路线

按“问题—障碍—信息—复用—验证—应用”的路线组织技术讲解。

### 问题

先给读者一个具体目标。例如不要直接说“前缀函数定义如下”，而应先展示字符串匹配失配后退回起点造成了哪些重复比较。

### 障碍

写出朴素方法，并用一个小例子指出慢在哪里。只有读者看见了浪费，优化才不是凭空出现的模板。

### 信息

明确要保存什么已经算出的信息。每个数组或状态都用一句可检验的话定义，并固定下标、区间和边界约定。

### 复用

说明旧信息怎样减少新工作。这通常是全文最值得详细展开的部分：镜像来自哪里、候选状态为什么完整、哪一段比较可以跳过。

### 验证

分别回答正确性和效率：为什么不漏答案、为什么不会重复做过多工作。不要用“显然”“容易发现”跳过关键台阶。

### 应用

把核心信息放进真实题目，展示识别信号、建模过程和实现边界。例题不是正文后的装饰，而是检验读者是否真的会用。

## 如何分配详略

详略得当并不等于每一节长度相近，而是把篇幅放在最可能产生理解跃迁的位置。

### 应详细展开

- 新定义与旧概念之间的关系；
- 从朴素做法到优化方法的关键跳跃；
- 正确性依赖的核心不变量；
- 摊还复杂度中“单次可能很慢、总量仍然很快”的原因；
- 下标、闭开区间、哨兵和边界条件；
- 例题中从题意识别算法的过程；
- 容易出现合理但错误直觉的地方。

### 应保持简洁

- 标准输入输出和项目已有的基础语法；
- 与正文相同逻辑的机械重复；
- 只需一句话即可交代的历史背景；
- 与主线弱相关的高级变体；
- 可以由清晰变量名直接表达的逐行代码翻译。

### 判断某段是否过长

逐段询问：删去它后，读者是否仍能推出下一步？若能，考虑压缩；若不能，检查是否缺少例子、定义或中间推理，而不是继续堆结论。

## 推荐文章骨架

以下是可调整的骨架，不是强制目录：

```text
标题
├─ 一句话说明解决什么问题、达到什么复杂度
├─ 具体动机或朴素方法
├─ 术语、符号与状态定义
├─ 核心推导
│  ├─ 小例子或状态表
│  ├─ 不变量／转移
│  └─ 正确性与复杂度
├─ 模板或接口代码
├─ 真实例题
│  ├─ 题意与识别线索
│  ├─ 思路
│  ├─ 完整代码
│  └─ 复杂度
├─ 进一步应用或相邻知识
├─ 易错点
└─ 小结
```

一个页面应围绕一个中心问题。若第二个算法需要重新引入定义、推导和模板，应拆成另一页；索引页负责说明二者关系和学习顺序。

## 定义、推导与证明

### 定义必须可执行

避免“它表示匹配情况”一类模糊表达。应说明：

- 对象是什么；
- 下标从哪里开始；
- 区间是否包含端点；
- 数值计数的是长度、位置还是数量；
- 空串、越界或首项如何约定。

定义后立刻配一个小例子，最好把数组或状态写成表格，让读者能够自己重新算出数值。

### 推导要保留中间桥梁

不要从朴素复杂度直接跳到最终公式。把推导拆为：

1. 哪些工作被重复；
2. 哪项旧信息能够代表这些工作；
3. 旧信息可以安全复用到什么边界；
4. 超出边界后还需要做什么；
5. 新结果如何更新维护的信息。

### 证明围绕风险写

正确性证明不必追求论文式形式化，但必须回答最危险的问题：

- 候选是否完整，会不会漏掉答案；
- 被跳过的比较为何已知相等；
- 贪心选择是否阻碍后续最优解；
- 状态转移是否重复或遗漏计数。

复杂度证明要说明计数对象。若有嵌套循环，指出指针、边界、势能或数据结构元素在整个算法中最多变化多少次。

## 例题的选择与讲法

### 选择标准

优先选择满足以下条件的真实题目：

- 题目来源与链接稳定；
- 数据范围确实要求该算法；
- 核心难点能体现正文刚建立的信息；
- 实现包含值得提醒的边界，但不会被无关技巧喧宾夺主。

模板题可以用于确认基本实现，但至少补充“为什么题意对应这个模板”。综合题适合展示知识点如何与 DP、二分、数据结构等组合。

### 讲题顺序

1. 用自己的话压缩题意，不大段转录原题。
2. 从数据范围排除过慢做法。
3. 指出题目中的识别信号。
4. 将题意对象映射到正文定义的状态或数组。
5. 给出算法步骤、正确性要点和复杂度。
6. 最后给完整代码，并解释仅有的非显然实现。

## 代码如何服务讲解

代码应是论证的落地版本，而不是另起一套叙事。

- 让正文中的 `left/right/rank/height` 等符号与代码保持一致。
- 在代码前解释数组语义，在代码后解释关键边界。
- 模板代码展示清晰接口；例题代码保证可独立编译运行。
- 不把大量解释写成行尾注释；正文解释思想，代码注释维护不变量。
- 不为了缩短而使用难读宏、含糊单字母变量或高度压缩表达式。
- 说明字符集、整数范围、递归深度、内存规模等实现前提。

验证至少包括：

1. C++17 语法检查；
2. 题目样例；
3. 一个最小边界；
4. 一个容易触发最坏情况或下标错误的构造。

高风险算法应与朴素实现做小规模随机对拍。

## 图解如何服务推理

先判断文字是否已经足够。只有图能同时呈现多个位置、分支或层级关系时再使用。

适合图解的内容包括：

- 一个区间内部的镜像、指针和边界；
- 树、图、递归调用或状态依赖；
- 算法跨多个阶段的状态变化；
- 多个数组之间的精确对应关系。

图解必须做到：

- 使用正文已经定义的术语；
- 标清方向、端点和下标约定；
- 图前说明观察目标，图后给出由图得到的结论；
- 保持小而聚焦，不绘制与推理无关的装饰元素。

## 资料学习与独立写作

参考优秀文章时，学习以下层面：

- 作者在哪里放慢速度解释核心性质；
- 如何用失败过程或例子制造学习动机；
- 证明、模板和例题之间如何衔接；
- 哪些扩展只点到为止并交给独立章节。

不要继承以下内容：

- 原文句子、段落顺序或独特比喻；
- 仅替换变量名的代码；
- 原文特有的例子组合；
- 没有自行核验的结论和题目描述。

从至少一个可靠来源核验关键事实。技术问题优先使用官方文档、竞赛大纲、原题页面或经典论文；引用应靠近所支持的内容。尽量转述，不进行长段引用，并明确区分事实、来源结论和自己的推断。

## 常见失败模式

- **百科式罗列**：定义很多，却没有一个问题推动读者继续读。
- **模板先行**：先贴代码，再逐行翻译，读者不知道为什么这样写。
- **证明缺席**：用“显然是线性的”代替总量分析。
- **例题悬空**：只给题目链接，不说明识别和建模过程。
- **代码与正文脱节**：下标、变量或区间约定不一致。
- **平均用力**：简单步骤写得很长，真正困难的转移只写一句。
- **一文塞满主题**：多个算法共享一个标题，却各自缺乏完整推导。
- **拓展反客为主**：高级算法篇幅超过目标考纲内的主线内容。
- **把图当装饰**：图中信息不能用于推出任何正文结论。
- **近似改写来源**：保留参考文章的结构和表达，只做同义替换。

## 完稿检查表

### 内容

- [ ] 开头明确问题、输入对象和目标。
- [ ] 朴素方法的瓶颈被具体展示。
- [ ] 每个状态、数组和区间都有精确定义。
- [ ] 核心优化从旧信息自然推导出来。
- [ ] 正确性和复杂度有独立解释。
- [ ] 主线与拓展的层级明确。

### 例题与代码

- [ ] 至少有一个可手算的小例子。
- [ ] 至少有一道真实且匹配知识点的题目。
- [ ] 例题包含识别线索、思路、实现和复杂度。
- [ ] 完整代码能按项目标准编译。
- [ ] 样例和关键边界经过实际验证。

### 表达与来源

- [ ] 重点处详细，机械步骤简洁。
- [ ] 图表确实降低了理解成本。
- [ ] 术语、符号和代码命名一致。
- [ ] 没有依赖读者回看参考文章才能理解的内容。
- [ ] 没有照抄、近似改写或超量引用。
- [ ] 来源链接准确并靠近所支持内容。
