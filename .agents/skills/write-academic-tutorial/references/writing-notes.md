## 写作目标

一篇好的学术讲解不是知识清单，也不是代码仓库。它应帮助读者完成三次转变：

1. 从“不知道问题为何困难”到能指出朴素方法的瓶颈；
2. 从“记住结论”到理解状态、公式或不变量为什么成立；
3. 从“看懂模板”到能在新题中识别条件、选择方法并正确实现。

文章应同时保证：

- **准确**：定义、命题、边界和复杂度经得起核对；
- **可学**：信息顺序符合读者建立模型的过程；
- **可用**：例题与代码把抽象结论落实到解题过程；
- **有层次**：主线完整，拓展明确，但不让次要内容淹没核心。

## 读者的认知路线

按“问题—障碍—信息—复用—验证—应用”的路线组织技术讲解。

### 问题

先给读者一个具体目标。例如不要直接说“前缀函数定义如下”，而应先展示字符串匹配失配后退回起点造成了哪些重复比较。

### 障碍

写出朴素方法，并用一个小例子指出慢在哪里。只有读者看见了浪费，优化才不是凭空出现的模板。

### 信息

明确要保存什么已经算出的信息。每个数组或状态都用一句可检验的话定义，并固定下标、区间和边界约定。

### 复用

说明旧信息怎样减少新工作。这通常是全文最值得详细展开的部分：镜像来自哪里、候选状态为什么完整、哪一段比较可以跳过。

### 验证

分别回答正确性和效率：为什么不漏答案、为什么不会重复做过多工作。不要用“显然”“容易发现”跳过关键台阶。

### 应用

把核心信息放进真实题目，展示识别信号、建模过程和实现边界。例题不是正文后的装饰，而是检验读者是否真的会用。

## 如何分配详略

详略得当并不等于每一节长度相近，而是把篇幅放在最可能产生理解跃迁的位置。

### 应详细展开

- 新定义与旧概念之间的关系；
- 从朴素做法到优化方法的关键跳跃；
- 正确性依赖的核心不变量；
- 摊还复杂度中“单次可能很慢、总量仍然很快”的原因；
- 下标、闭开区间、哨兵和边界条件；
- 例题中从题意识别算法的过程；
- 容易出现合理但错误直觉的地方。

### 应保持简洁

- 标准输入输出和项目已有的基础语法；
- 与正文相同逻辑的机械重复；
- 只需一句话即可交代的历史背景；
- 与主线弱相关的高级变体；
- 可以由清晰变量名直接表达的逐行代码翻译。

### 判断某段是否过长

逐段询问：删去它后，读者是否仍能推出下一步？若能，考虑压缩；若不能，检查是否缺少例子、定义或中间推理，而不是继续堆结论。

## 推荐文章骨架

以下是可调整的骨架，不是强制目录：

```text
标题
├─ 一句话说明解决什么问题、达到什么复杂度
├─ 具体动机或朴素方法
├─ 术语、符号与状态定义
├─ 核心推导
│  ├─ 小例子或状态表
│  ├─ 不变量／转移
│  └─ 正确性与复杂度
├─ 模板或接口代码
├─ 真实例题
│  ├─ 题意与识别线索
│  ├─ 思路
│  ├─ 完整代码
│  └─ 复杂度
├─ 进一步应用或相邻知识
├─ 易错点
└─ 小结
```

一个页面应围绕一个中心问题。若第二个算法需要重新引入定义、推导和模板，应拆成另一页；索引页负责说明二者关系和学习顺序。

## 定义、推导与证明

### 定义必须可执行

避免“它表示匹配情况”一类模糊表达。应说明：

- 对象是什么；
- 下标从哪里开始；
- 区间是否包含端点；
- 数值计数的是长度、位置还是数量；
- 空串、越界或首项如何约定。

定义后立刻配一个小例子，最好把数组或状态写成表格，让读者能够自己重新算出数值。

### 推导要保留中间桥梁

不要从朴素复杂度直接跳到最终公式。把推导拆为：

1. 哪些工作被重复；
2. 哪项旧信息能够代表这些工作；
3. 旧信息可以安全复用到什么边界；
4. 超出边界后还需要做什么；
5. 新结果如何更新维护的信息。

### 证明围绕风险写

正确性证明不必追求论文式形式化，但必须回答最危险的问题：

- 候选是否完整，会不会漏掉答案；
- 被跳过的比较为何已知相等；
- 贪心选择是否阻碍后续最优解；
- 状态转移是否重复或遗漏计数。

复杂度证明要说明计数对象。若有嵌套循环，指出指针、边界、势能或数据结构元素在整个算法中最多变化多少次。

## 例题的选择与讲法

### 选择标准

优先选择满足以下条件的真实题目：

- 题目来源与链接稳定；
- 数据范围确实要求该算法；
- 核心难点能体现正文刚建立的信息；
- 实现包含值得提醒的边界，但不会被无关技巧喧宾夺主。

模板题可以用于确认基本实现，但至少补充“为什么题意对应这个模板”。综合题适合展示知识点如何与 DP、二分、数据结构等组合。

### 讲题顺序

1. 用自己的话压缩题意，不大段转录原题。
2. 从数据范围排除过慢做法。
3. 指出题目中的识别信号。
4. 将题意对象映射到正文定义的状态或数组。
5. 给出算法步骤、正确性要点和复杂度。
6. 最后给完整代码，并解释仅有的非显然实现。

## 代码如何服务讲解

代码应是论证的落地版本，而不是另起一套叙事。

- 让正文中的 `left/right/rank/height` 等符号与代码保持一致。
- 在代码前解释数组语义，在代码后解释关键边界。
- 模板代码展示清晰接口；例题代码保证可独立编译运行。
- 不把大量解释写成行尾注释；正文解释思想，代码注释维护不变量。
- 不为了缩短而使用难读宏、含糊单字母变量或高度压缩表达式。
- 说明字符集、整数范围、递归深度、内存规模等实现前提。

验证至少包括：

1. C++17 语法检查；
2. 题目样例；
3. 一个最小边界；
4. 一个容易触发最坏情况或下标错误的构造。

高风险算法应与朴素实现做小规模随机对拍。

## 图解如何服务推理

先判断文字是否已经足够。只有图能同时呈现多个位置、分支或层级关系时再使用。

适合图解的内容包括：

- 一个区间内部的镜像、指针和边界；
- 树、图、递归调用或状态依赖；
- 算法跨多个阶段的状态变化；
- 多个数组之间的精确对应关系。

图解必须做到：

- 使用正文已经定义的术语；
- 标清方向、端点和下标约定；
- 图前说明观察目标，图后给出由图得到的结论；
- 保持小而聚焦，不绘制与推理无关的装饰元素。

## 资料学习与独立写作

参考优秀文章时，学习以下层面：

- 作者在哪里放慢速度解释核心性质；
- 如何用失败过程或例子制造学习动机；
- 证明、模板和例题之间如何衔接；
- 哪些扩展只点到为止并交给独立章节。

不要继承以下内容：

- 原文句子、段落顺序或独特比喻；
- 仅替换变量名的代码；
- 原文特有的例子组合；
- 没有自行核验的结论和题目描述。

从至少一个可靠来源核验关键事实。技术问题优先使用官方文档、竞赛大纲、原题页面或经典论文；引用应靠近所支持的内容。尽量转述，不进行长段引用，并明确区分事实、来源结论和自己的推断。

## 常见失败模式

- **百科式罗列**：定义很多，却没有一个问题推动读者继续读。
- **模板先行**：先贴代码，再逐行翻译，读者不知道为什么这样写。
- **证明缺席**：用“显然是线性的”代替总量分析。
- **例题悬空**：只给题目链接，不说明识别和建模过程。
- **代码与正文脱节**：下标、变量或区间约定不一致。
- **平均用力**：简单步骤写得很长，真正困难的转移只写一句。
- **一文塞满主题**：多个算法共享一个标题，却各自缺乏完整推导。
- **拓展反客为主**：高级算法篇幅超过目标考纲内的主线内容。
- **把图当装饰**：图中信息不能用于推出任何正文结论。
- **近似改写来源**：保留参考文章的结构和表达，只做同义替换。

## 从优秀文章提炼的方法

以下笔记只提炼可复用的写作方法，不复制原文措辞、代码、例题组合或章节顺序。

### 定义、定理与算法形成因果链

[《NOI 一轮复习 I：二分图网络流》](https://www.luogu.com/article/7jvdcurk)的可取之处是先声明范围和假设，再从精确定义出发，给出定理及证明，最后由证明过程导出判定或构造算法。学习这种“定义—性质—证明—算法—建模”的连接方式：算法中的每一步应能在前文找到理论依据，定理也应在后续算法或例题中真正使用。

对构造型结论分别证明两件事：构造出的对象合法，以及它达到所声称的最优值。对“方案对应模型”的说法证明两个方向，避免只凭图形直觉声称等价。

不要继承该文明确省略复杂度或模板细节的做法。本站教程必须补齐实现对应的时间、空间复杂度和关键代码说明。

### 用多种视角跨过最难的推导

[《数论函数与筛法（Part 1）》](https://www.cnblogs.com/alex-wei/p/19673860)先统一符号，并主动区分容易混淆的相邻概念；推导线性筛时先指出重复筛除，再比较两条可能路线，最后解释循环为何在特定条件处停止。关键结论还会从代数关系、容斥直觉和递推系数等不同视角推导。

学习其“多视角只服务关键难点”的节奏：普通步骤保持简洁，对最反直觉的公式或条件提供第二种解释。不同推导不能只是换符号重复同一过程，应分别服务形式证明、直觉理解或实现判断。代码必须放在推导之后，并明确指出 `break`、边界或更新顺序对应的数学原因。

### 索引页说明路线、状态和适用对象

[《Blog 索引（置顶）》](https://www.luogu.com.cn/article/pcikmsis)不只是链接集合，还标明文章的完成度、推荐程度、内容侧重和适合的读者。本站索引页也应告诉读者先学什么、页面解决什么、属于主线还是拓展、是否已经完整审校。

索引组织方法不能直接搬到正文。一篇教程仍应围绕一个中心知识点；不要把大量页面摘要、难度标签或主题列表塞进单篇讲解。

### 用例题提炼方法，而不是堆题

[《dp 题方法总汇》](https://www.luogu.com.cn/article/ki71nw88)先说明前置知识与文章定位，再把动态规划思考拆成分析性质、处理模型、设计状态和优化等阶段。许多例题不仅给出结果，还比较生成顺序、状态选择或多种解法，并在结尾提炼“状态封闭性”“无关性”“延后决策”等可迁移认识。

学习这种“例题反哺方法论”的方式：每道例题结尾明确写出本题验证了正文中的哪项原则、识别信号是什么、换一个表面条件后哪些部分仍可复用。本站面向系统学习者，不能继承其省略题意、完整题解和代码的题单式写法；核心例题仍须完整讲解。

### 综合采用的文章节奏

1. 开头声明读者前提、范围、目标和不讨论的内容。
2. 用一个具体障碍建立动机，再统一术语、符号和约定。
3. 沿一条主要因果链推进；在最困难处增加反例、失败思路或第二视角。
4. 让证明导出算法，让算法落到手算例子，让例题提炼出迁移方法。
5. 结尾给边界、易错点和下一步路线；索引页另行管理页面状态与学习顺序。

## 四维质量标准

### 严谨性

把每个核心论证写成“前提—对象—结论—理由—边界”的闭环：

- 定义列出对象、取值范围、下标、区间和特殊情况；
- 定理不得隐藏连通性、非负性、单调性、无重边等前提；
- 双向命题拆开证明充分性与必要性；
- 贪心证明说明交换或支配关系，动态规划证明说明状态完备、转移不漏不重；
- 摊还分析指出被计数对象在全程最多变化多少次；
- 概率算法写明碰撞风险和降低风险的方法，不称为绝对正确；
- 关键前提容易被忽视时给一个删除该前提就失败的反例。

### 易懂性

同一难点依次提供三层解释：

1. **直觉层**：用小对象或失败过程说明为什么需要新信息。
2. **形式层**：用定义、公式和不变量说明它为什么成立。
3. **执行层**：用状态表、伪代码或程序说明怎样算出来。

新术语首次出现时先用一句普通语言定位，再给正式定义。新公式出现前说明求什么，出现后逐项解释来源，并用小数据验算。不得让读者通过猜测补上“因此”两侧的逻辑。

### 详细程度

详细不等于篇幅长。以下位置必须放慢：

- 朴素方法到优化方法的第一次跳跃；
- 状态为何足够、为何无需记录更多信息；
- 转移如何覆盖全部候选且不重复；
- 特殊边界为何与一般情况不同；
- 嵌套循环为何仍满足所称复杂度；
- 题目对象如何映射为图、状态、区间或代数式；
- 实现中的停止条件、遍历顺序、哨兵和下标偏移。

若一段只列出若干结论、题号或代码，即使很长也不算详细。验收标准是目标读者能否仅凭本文重建推导、手算例子、说明正确性并独立实现。

### 例题的证据链

真实例题至少完整回答：

1. 数据范围排除了哪些朴素方法；
2. 哪些题面特征指向当前知识点；
3. 题目对象与算法对象如何逐项映射；
4. 算法为何得到且只得到合法答案；
5. 实现中哪些地方属于通用模板，哪些是本题特有处理；
6. 复杂度为何满足数据范围；
7. 哪个边界样例最容易推翻错误实现；
8. 本题留下了什么可迁移的识别信号。

## 代码可读性标准

代码是正文推导的可执行版本，不是为了展示短小的竞赛速写。

- 完整程序应独立编译，明确使用 C++17，并包含实际需要的头文件和命名空间。
- 用函数或类型隔离读入、预处理、核心算法和答案生成；函数名表达职责，参数表达依赖。
- 变量名与正文符号一致并体现角色，例如 `prefix_function`、`matching`、`residual_capacity`；短变量只用于局部循环或经典公式。
- 避免 `#define int long long`、难读宏、过度模板化、逗号表达式和一行多语句。
- 明确整数类型选择、乘法溢出、数组边界、递归深度、字符集和内存上限。
- 注释解释“不这样写会错在哪里”和维护的不变量，不翻译显而易见的赋值与循环。
- 在正文中解释最难的代码块与推导的对应关系，并标明模板接口和题目特化部分。
- 除编译和样例外，运行最小边界、最大风险构造；能够写朴素算法时进行小规模随机对拍。

## 二次自审流程

初稿完成不等于任务完成。先进行要求覆盖审查，修正后再做一次独立复核，避免作者因为熟悉自己的表达而忽略缺口。

### 第一遍：要求覆盖审查

1. 重新阅读用户的全部要求、仓库规范和文章目标，列出明确的验收项。
2. 为每个验收项找到正文、代码、图表或验证结果中的对应证据；找不到证据即视为尚未完成。
3. 逐项核对定义、推导、正确性、复杂度、例题、代码、边界、来源和考纲范围。
4. 检查改动范围与 Git 差异，排除遗漏、重复和无关修改。
5. 修正发现的问题，并重新运行受影响的编译、样例、链接或构建检查。

### 第二遍：独立复核

修正完成后暂时放下写作者视角，把文章当作第一次看到的读者或审稿者来阅读。再次询问：仅凭本文能否理解推导、复现代码并判断适用边界？重新核对要求覆盖和验证记录，而不是只浏览上一遍修改的位置。若又发现问题，修正后重复相应检查。

术语与缩写需要单独复核：

- 专业缩写首次出现时写出全称，例如“最长公共前缀（Longest Common Prefix，LCP）”；
- 同一概念的中英文名称和缩写在全文保持一致；
- 同一个缩写不能在一篇文章中指代两个概念；
- 非通行缩写必须明确定义，不能为了省字自行缩写；
- 标题、图表、公式、正文和代码中的符号不能互相冲突。

交付说明应记录两遍自审实际检查了什么、自审中修正了什么，以及仍无法消除的警告或不确定项。无法实际验证时应如实说明，不能用“应当可以”代替验证结果。

复核结束后同步维护版本记录：已完成的增删改和本次已修复问题写入根目录 `CHANGELOG.md` 的“未发布”部分；未解决、无法核验或计划延后的问题写入 `TODO.md` 的“审核发现”，并给出优先级和复查证据。已经完成的事项应从 TODO 移除，不能同时以“已完成”状态长期留在待办清单中。
