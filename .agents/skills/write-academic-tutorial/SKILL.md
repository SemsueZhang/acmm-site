# 撰写学术讲解类博客

## 准备

在开始撰写或大幅重写前，完整阅读 [references/writing-notes.md](references/writing-notes.md)。把它作为写作标准与检查表，不要把其中的模板机械复制到正文。

先确认以下信息；能从仓库、题目或上下文查明时直接查明，不要反复询问用户：

1. 明确读者基础、文章目标和知识范围。
2. 明确哪些内容是主线必学，哪些属于拓展。
3. 检查同目录文章、导航、术语和代码风格。
4. 查阅可靠资料核对定义、定理、复杂度和题目要求。
5. 只学习参考资料的组织方式和论证节奏，不复制其表达、例子结构或代码。

先列出本文必须回答的问题、读者需要的前置知识和最终应获得的能力。若现有资料不足以核验结论、题目或代码，先查证，不要用流畅表达掩盖事实缺口。

## 坚守质量底线

同时满足以下四项要求；任何一项不足都不能以其他项篇幅较长来补偿：

1. **严谨性**：精确定义对象、符号、下标、区间和前提；定理写清条件与结论；正确性论证覆盖不遗漏、不重复和终止性等真实风险；复杂度与实际实现一致。
2. **易懂性**：先给直觉和具体障碍，再给形式化表述；每个新概念说明“为何需要、从何而来、解决什么”；关键公式前后都有自然语言解释。
3. **详细程度**：详细展开产生理解跃迁的步骤，不用“显然”“容易得”跳过核心推导；每次从旧结论跳到新状态、公式或优化时补齐中间桥梁。
4. **代码可读性**：实现与正文使用同一套语义；优先清晰的函数、类型、变量名和控制流，不为缩短代码使用难读宏、隐含状态或压缩写法。

把讲解分成三个互相校验的层次：直觉层回答“为什么想到”，形式层回答“为什么成立”，执行层回答“如何算、如何写、如何验证”。三层缺一不可。

## 设计讲解主线

围绕读者会依次提出的问题组织文章：

1. 这个问题为什么值得解决？
2. 朴素方法怎么做，瓶颈在哪里？
3. 新定义或状态具体表示什么？
4. 优化如何从已知信息自然推出？
5. 为什么正确，为什么达到所称复杂度？
6. 在真实题目中怎样识别和使用？
7. 哪些边界、变体或误区最容易出错？

先画出知识依赖与结论链：前置概念支持哪个性质，性质怎样导出算法，算法怎样解决例题。若某个结论不能接入这条链，压缩、移到拓展页或删除。索引页负责呈现学习路线、适用范围和页面完成度，正文页不要承担整个主题的百科式汇总。

一个知识点只保留一条主要推导线。若多个算法只有主题相关而推导相对独立，拆成单独文章，并由索引页说明学习顺序和范围。

## 撰写正文

按内容需要选用以下结构，不为凑齐标题而生搬硬套：

1. 用一个具体问题、失败过程或反例引出动机。
2. 定义术语、符号、下标和区间约定。
3. 先说明朴素做法，再定位重复工作或性能瓶颈。
4. 至少展示一次失败尝试、反例或不能直接优化的原因，让最终方法有可追溯的来源。
5. 分步推导核心转移、不变量或数据结构操作；每个公式先定义全部符号，再说明每一项的来源。
6. 对核心定理写明前提、结论和证明。双向命题分别证明两个方向；构造性结论同时说明构造为何合法且达到目标。
7. 单独解释正确性与复杂度；避免只写结论，并指出删除关键前提后会出现的失败情况。
8. 用小型手算示例逐步跟踪状态，确保读者能够独立复算。
9. 配置至少一道真实例题，说明数据范围、识别线索、朴素瓶颈、建模映射、算法、正确性、实现和复杂度。
10. 给出与网站一致的完整代码；模板片段必须说明输入、输出、接口语义和使用前提。
11. 总结常见错误、适用边界、相邻知识点和下一步学习方向。

保持详略有别：详细展开产生理解跃迁的部分，压缩机械性步骤。对核心不变量、容易误解的下标和复杂度摊还过程多解释；对标准输入输出、显然循环和重复代码少解释。

不得用篇幅代替细节。连续罗列定义、定理、题目或代码，即使很长，也不算详细。判断一段是否充分时，检查读者能否仅凭本文重建下一步推导、手算小例子并解释关键代码；不能做到就补充缺失的桥梁，而不是继续堆结论。

## 使用例题与代码

选择能够体现本知识点核心信息的真实题目，不要只选择“套模板即可”的题目。先讲清题目为什么对应当前算法，再给代码。

至少安排两层例证：用一个小例子解释机制，用一道真实题解释识别和建模。需要展示迁移能力时，再增加一道改变表面条件但复用同一不变量的题；不要用大量只给一句思路的题目代替完整讲解。

讲解真实题时，将题目对象与算法对象逐项对应，例如“点表示什么、边表示什么、容量限制什么、状态保存什么”。若声称两种方案一一对应，分别证明正向构造和反向还原。比较多种思路时，说明每种思路失败或较慢的具体原因，并提炼最终可复用的识别信号。

编写代码时：

- 默认使用项目约定的语言和版本；本仓库算法文章使用 C++17。
- 统一下标、区间端点、返回值和空情况的定义。
- 让变量名对应正文符号，避免正文与实现使用两套概念。
- 按职责拆分函数或类型，使输入、输出和副作用可见；避免依赖难以追踪的全局状态。
- 使用能表达角色的变量名；只在数学惯例明确且作用域很小时使用 `i`、`j` 等短名称。
- 避免 `#define int long long`、难读宏、逗号表达式和把多项逻辑压在一行的写法。
- 只注释关键不变量、非显然操作和易错边界；不要用注释逐行翻译代码。
- 给出时间、空间复杂度，并确认与实现一致。
- 说明整数范围、溢出风险、递归深度、字符集、哨兵和内存规模等实现前提。
- 实际进行语法检查；对完整程序至少运行代表性样例。

在代码前给出接口约定和关键数据语义；在代码后选择最难的若干代码块与正文推导对应，不要贴完代码便结束。模板与例题程序分开时，解释二者差异，避免读者把特定题目的处理误当成通用模板。

## 使用图解

仅在图能明显降低理解成本时加入图解。优先使用仓库可直接渲染的 Mermaid：

- 用时间线或流程图表现状态推进。
- 用树或层级图表现递归、Trie、失配树等结构。
- 用区间图表现双指针、回文半径、Z-box 等位置关系。
- 用表格表现数组值、状态含义或方案对比。

让正文先定义图中的符号，并在图后解释读图所得结论。不要用装饰性图解替代证明。

## 核查与交付

完成初稿或实现后不得立即交付，必须进行两遍自审。第一遍逐项核对要求并修正问题；修正完成后，再从读者和审稿者的视角独立进行第二遍复核，不能只重读刚改过的句子。

第一遍按以下顺序检查：

1. 重新阅读用户的全部要求、仓库 `AGENTS.md` 和本技能，将每项要求对应到具体页面、段落、代码或验证结果，检查遗漏与越界修改。
2. 核对每个术语、定义、公式、下标、边界、正确性论证和复杂度。
3. 检查术语与缩写：首次出现时给出中文或英文全称及缩写，后文用法保持一致；不得使用未定义、非通行或一词多义的缩写。
4. 检查例题链接、题意、数据范围与所用算法是否真实、准确。
5. 检查代码能否按项目标准编译，样例和关键边界是否实际通过；高风险算法按需随机对拍。
6. 检查站内链接、导航和页面构建，并区分本次问题与仓库已有警告。
7. 检查是否误把高阶拓展写成基础必修内容，是否存在来源依赖过重、近似改写或长段引用。
8. 检查文章能否脱离参考资料独立阅读，并审阅 Git 差异和状态，排除无关、遗漏或意外改动。
9. 逐项执行严谨性、易懂性、详细程度和代码可读性检查：不能为每项指出正文证据时，视为未通过。

发现问题后先修正，再重新执行受影响的验证。第二遍复核应再次检查要求覆盖、技术正确性、表达一致性和实际验证结果；未通过时继续修正，不得宣称完成。无法核验的项目必须明确说明原因和影响。

完成两遍自审后，同步维护仓库根目录的版本记录：

- 在 `CHANGELOG.md` 的“未发布”部分按新增、修改、修复、删除记录本次实际变化和本次已解决的审核问题。
- 将本次未解决、无法核验或需要后续处理的问题加入 `TODO.md` 的“审核发现”，注明优先级、修改对象和复查证据。
- 从 `TODO.md` 移除本次已经完成的事项，并确认其解决结果已进入 `CHANGELOG.md`。
- 对照文章差异检查两个记录文件，避免遗漏、重复或使用无法验证的笼统描述。

交付时简要说明新增或重写了什么、两遍自审与验证做了什么、自审中修正了什么，以及仍存在的警告或不确定项。只有用户明确要求时才执行提交、推送或发布。
