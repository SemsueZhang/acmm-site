# 撰写学术讲解类博客

## 准备

在开始撰写或大幅重写前，完整阅读 [references/writing-notes.md](references/writing-notes.md)。把它作为写作标准与检查表，不要把其中的模板机械复制到正文。

先确认以下信息；能从仓库、题目或上下文查明时直接查明，不要反复询问用户：

1. 明确读者基础、文章目标和知识范围。
2. 明确哪些内容是主线必学，哪些属于拓展。
3. 检查同目录文章、导航、术语和代码风格。
4. 查阅可靠资料核对定义、定理、复杂度和题目要求。
5. 只学习参考资料的组织方式和论证节奏，不复制其表达、例子结构或代码。

## 设计讲解主线

围绕读者会依次提出的问题组织文章：

1. 这个问题为什么值得解决？
2. 朴素方法怎么做，瓶颈在哪里？
3. 新定义或状态具体表示什么？
4. 优化如何从已知信息自然推出？
5. 为什么正确，为什么达到所称复杂度？
6. 在真实题目中怎样识别和使用？
7. 哪些边界、变体或误区最容易出错？

一个知识点只保留一条主要推导线。若多个算法只有主题相关而推导相对独立，拆成单独文章，并由索引页说明学习顺序和范围。

## 撰写正文

按内容需要选用以下结构，不为凑齐标题而生搬硬套：

1. 用一个具体问题、失败过程或反例引出动机。
2. 定义术语、符号、下标和区间约定。
3. 先说明朴素做法，再定位重复工作或性能瓶颈。
4. 分步推导核心转移、不变量或数据结构操作。
5. 单独解释正确性与复杂度；避免只写结论。
6. 用小型手算示例跟踪关键状态。
7. 配置至少一道真实例题，说明识别线索、建模、实现和复杂度。
8. 给出与网站一致的完整代码；模板片段必须说明接口语义。
9. 总结常见错误、适用边界和与相邻知识点的联系。

保持详略有别：详细展开产生理解跃迁的部分，压缩机械性步骤。对核心不变量、容易误解的下标和复杂度摊还过程多解释；对标准输入输出、显然循环和重复代码少解释。

## 使用例题与代码

选择能够体现本知识点核心信息的真实题目，不要只选择“套模板即可”的题目。先讲清题目为什么对应当前算法，再给代码。

编写代码时：

- 默认使用项目约定的语言和版本；本仓库算法文章使用 C++17。
- 统一下标、区间端点、返回值和空情况的定义。
- 让变量名对应正文符号，避免正文与实现使用两套概念。
- 只注释关键不变量、非显然操作和易错边界。
- 给出时间、空间复杂度，并确认与实现一致。
- 实际进行语法检查；对完整程序至少运行代表性样例。

## 使用图解

仅在图能明显降低理解成本时加入图解。优先使用仓库可直接渲染的 Mermaid：

- 用时间线或流程图表现状态推进。
- 用树或层级图表现递归、Trie、失配树等结构。
- 用区间图表现双指针、回文半径、Z-box 等位置关系。
- 用表格表现数组值、状态含义或方案对比。

让正文先定义图中的符号，并在图后解释读图所得结论。不要用装饰性图解替代证明。

## 核查与交付

完成后依次检查：

1. 核对每个术语、公式、边界和复杂度。
2. 检查例题链接与题意是否真实、准确。
3. 检查代码能否编译，样例是否通过。
4. 检查站内链接、导航和页面构建。
5. 检查是否误把高阶拓展写成基础必修内容。
6. 检查是否存在来源依赖过重、近似改写或长段引用。
7. 检查文章能否脱离参考资料独立阅读。

交付时简要说明新增或重写了什么、验证了什么、是否存在遗留警告。只有用户明确要求时才执行提交、推送或发布。
